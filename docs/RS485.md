## Physical layout

Use RS-485 transceivers/adapters, not bare RS-232 ports or direct UART pins. A
common two-wire half-duplex layout is a linear trunk with short stubs:

```text
Termination                                          Termination
    |                                                     |
====+==============+================+=====================+====
                   |                |                     |
             coordinator 0       client 1              server 2
```

RS-485 is an electrical interface; the project's polling protocol supplies bus
ownership and frame addressing. A shared half-duplex pair must not be driven by
two nodes simultaneously [1].

Match termination to the cable's characteristic impedance; a 120-ohm twisted-pair
cable normally uses one 120-ohm termination at each physical end, not at every
node. Keep stubs short and avoid a star topology for the initial lab [1].

Check whether adapters already include termination and fail-safe bias resistors.
Do not blindly enable bias networks at every node. Provide a suitable signal
reference within transceiver common-mode limits; use isolation when grounds may
differ. Follow adapter and transceiver documentation for grounding, shielding,
isolation, connector pinout and allowable voltage differences. A/B or +/- labels
are not consistent across all vendors: verify polarity from their documentation,
not merely from matching letters [1].

Only one node may be the coordinator, and every node must have a unique ID.
All devices must use the same baud rate, framing settings, neighbor map,
coordinator ID and compatible timing settings.

## Adapter direction modes

`--direction auto` uses normal pySerial writes and assumes the converter itself
automatically enables its transmitter for the bytes and releases the bus after
the last stop bit. It does not discover or configure an adapter's jumpers.

`--direction native` configures `Serial.rs485_mode` with `RS485Settings` before
opening the port. The operating system and driver then manage RTS during
transmission. Actual support varies by platform, driver and hardware; some
Windows configurations support only restricted RTS-on-transmit behavior [2].

`--rts-active-low` reverses the requested RTS polarity. Use it only when required
by the adapter's DE wiring. Native-mode failures are reported, not silently
replaced with manually timed RTS. pySerial warns that user-space RTS emulation
can be unreliable due to control-signal and scheduling delays [2].

## Example configuration

Each machine keeps the following file as `examples/three_nodes.json`:

```json
{
  "10.0.0.1": 0,
  "10.0.0.2": 1,
  "10.0.0.3": 2
}
```

Run the commands in the README, substituting each computer's actual local port.
The coordinator derives its round-robin peer list from the complete map. Peers
are allowed to queue data before it starts, but will not transmit until polled.

The core allows IDs 0..254, with 255 reserved for link broadcast. This is an
addressing limit, not a supported hardware node count. RS-485 loading, cable,
transceivers, termination, biasing, timing and application throughput constrain
the physical installation [1].

## Timing setup

For 8N1, estimate serialization time as:

```text
wire_seconds = wire_bytes * 10 / baudrate
maximum_wire_bytes = 2 * (8 + 1024 + 4) + 2 = 2074
```

At 115200 baud this is approximately 0.180 seconds. At 9600 baud it is about
2.160 seconds, so the 0.5-second default response timeout is insufficient.
For a slow lab bus, use a larger value consistently, for example:

```console
python -m pynetstack node --port COM3 --node-id 0 --ip 10.0.0.1 --neighbors examples/three_nodes.json --baudrate 9600 --response-timeout 3
```

The default serial-mode TCP RTO is derived from node count and the polling timeout:
`max(3, 2 * node_count * (response_timeout + guard) + 1)` seconds. `--tcp-rto`
overrides it. Choose an RTO larger than an expected data/ACK round trip, including
polling, timeouts for absent nodes, escaping, serialization and USB scheduling.
A too-small value creates unnecessary retransmissions and queue pressure.

Do not treat the guard as a precision scheduler. Increase it when measured
turnaround times require it. Excessive application callbacks or pausing a
process in a debugger can violate timing assumptions. When debugging a physical
node, stop the coordinator or disconnect that node from the bus first.

## Bring-up procedure

First run `python -m pynetstack demo --quiet` and the unit tests. Then connect a
small isolated lab bus with correct termination/reference. Verify each serial
port can be opened. Start the peer processes and the single coordinator. Inspect
POLL and IDLE records before sending application data.

Send one short UDP echo, then ICMP echo, then TCP echo. Enable `--hex` or write
`--json node1.jsonl` to compare byte/frame/IP traces. Confirm direction switching
and turnaround timing with a logic analyzer or oscilloscope where available.
Finally test an absent node, larger payloads and sustained traffic; watch for CRC
failures, timeouts, duplicate IDs and queue exhaustion.

## Troubleshooting

| Observation | Checks |
|---|---|
| Port cannot open | Correct device name, permissions, competing process, driver, adapter connection |
| No POLL at peers | Coordinator running, common baud/framing, correct polarity and reference |
| Continuous timeouts | Peer ID/map, direction control, bus wiring, serial settings, read-loop latency |
| Frequent CRC failures | Termination, biasing, noise, cable/stubs, polarity, two active transmitters |
| UDP works but TCP retries frequently | RTO budget, poll round duration, missing peers, queue depth |
| `native` mode rejected | Unsupported driver/adapter; use hardware auto-direction only if it is actually available |
| OS ping fails | Expected: the IP addresses exist only within the teaching stack |
